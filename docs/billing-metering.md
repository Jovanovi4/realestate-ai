# Журнал расхода и учёт ресурсов без блокировок

Этап 3, 29 сентября 2026 года. Правила — [BP-0.1](billing-policy.md),
счета и периоды — [основа тарифного слоя](billing-foundation.md).
Этот документ описывает состояние этапа 3; последующие изменения резерва и
повторных запросов описаны в [этапе резервирования](billing-reservations.md).

`BILLING_SHADOW_ENABLED=True` включает наблюдение, а не запрет действий.
Кабинет, команды, XML и ИИ продолжают работать при превышении предварительных
лимитов. Платежей, автоматической очистки файлов и отключения лендингов нет.
Существующие проверки прав, CSRF, форм, безопасности загрузок и антиспама
остаются обязательными. Провайдер/модель не меняются; дополнительные запросы
к ИИ ради измерения расхода не отправляются.

## Что записывается

| Модель | Содержание |
| --- | --- |
| `UsageOperation` | Пространство, исполнитель, UUID, действие, ресурс, снимки условий/периода/решения, исход и технические метаданные провайдера |
| `UsageEntry` | Неизменяемое изменение количества ресурса или расход ИИ-кредитов |
| `StoredFile` | Принадлежность сохранённого файла, размер в байтах, состояние и код проблемы |
| `FileReference` | Связь файла с фотографией или логотипом объекта |
| `AccountInventory` | Полнота инвентаризации, время обновления и число проблем |
| `UsageResult` | Неизменяемая связь операции с реально сохранённым `AIContent` для восстановления учёта |

Ресурсы: активные и все объекты, опубликованные неархивные лендинги, сотрудники,
действующие приглашения, сохранённые байты, ИИ-кредиты. Скачивание XML фиксируется
как использование функции, без придуманной квоты количества выгрузок.

В журнале нет копий текстов, промптов, токенов API, имён/телефонов клиентов
или полных ответов провайдера. Сохраняются ID результатов и технические поля.
Реестр файлов хранит ключи хранилища: это служебные данные, не публичный отчёт.
Административный журнал доступен только уполномоченному персоналу и только для
чтения; операции и проводки имеют пагинацию по 25 записей.

## Ресурсы и файлы

Изменения обычных моделей наблюдаются после успешного коммита, включая формы,
HTMX, администрацию, демо и массовые действия, использующие `save()`/`delete()`.
Откат CRM-транзакции не оставляет успешной записи расхода. Личная область
строго отделена от базы агентства; тариф сотрудника не оплачивает общие ресурсы.

Файлы измеряются после сохранения и обработки изображения, а не по размеру
исходной загрузки. Один ключ файла внутри пространства считается один раз.
Фотографии демо и архива, логотипы и известные ранее принадлежавшие пространству
файлы входят в объём. Аватар профиля остаётся отдельным техническим ресурсом.

- Архив освобождает активный объект и публикацию, но не байты и не CRM-историю.
- Удаление ссылки/замена логотипа не доказывают физическое удаление файла.
  Оставшийся старый файл продолжает занимать байты до подтверждённого удаления.
  Этот этап не добавляет очистку таких файлов.
- Подтверждённое отсутствие даёт ноль байтов и отдельный код проблемы; ошибка
  чтения размера даёт `null`, не ноль. Пока инвентаризация неполная,
  `storage_bytes=null`, а предполагаемое решение — `usage_unknown`.
- Явный перенос ресурса перераспределяет принадлежность файла, не удаляя его.
  Повторный перенос обратно также учитывается.
- Неизвестные файлы без определённого владельца показываются в отдельной
  диагностике, не удаляются и не начисляются случайному аккаунту. Автоматический
  поиск таких файлов сейчас доступен только для локальных `properties/` и
  `landing_logos/`; удалённое хранилище требует отдельного средства инвентаризации.

При первом файловом изменении пространство проходит сверку ссылок. Далее
измеряются изменённые файлы; повторное сохранение всей CRM не сканирует каждый
объект хранилища заново. Сводка записей считается по БД, объём файлов — по
последней инвентаризации. Изменение файлов вне приложения, выключенный учёт,
прямой SQL или `QuerySet.update()`/`bulk_create()` требуют полной сверки.
`inventory.last_updated_at` — время обновления инвентаризации, не гарантия
проверки каждого физического файла в этот момент.

## Одна ИИ-генерация — одна операция

Все текущие пользовательские пути генерации используют
`observe_ai_generation(...)`: отдельные поля, комплекты, ИИ-ассистент,
улучшение, ответ на заявку и локальный аудит. Вызов провайдера выполняется
вне транзакции учёта. Полный пригодный результат сохраняется атомарно; три
или семь созданных текстов не превращаются в три или семь списаний.

Успешное сохранение добавляет одну проводку с весом операции из снимка условий.
Ошибка API, пустой/неполный результат или откат сохранения не списывают
пользовательские кредиты. Фактически возвращённые провайдером токены сохраняются
и при неудачном результате: неуспех для пользователя не означает отсутствие
затрат провайдера.

В Responses API сохраняются `input_tokens`, `output_tokens`, `total_tokens`,
кэшированные входные токены из `input_tokens_details.cached_tokens`, ID ответа,
модель и статус. В Ollama используются `prompt_eval_count`, `eval_count` и
доступные метаданные кэша. Форматы: [OpenAI Responses](https://developers.openai.com/api/reference/python/resources/responses/methods/create),
[Ollama generate](https://docs.ollama.com/api/generate).
Если usage отсутствует, поля остаются `null`. Денежная себестоимость не
вычисляется: версия цен/модели и финансовая политика будут отдельным этапом.

Жизненный цикл — `running` → `succeeded` / `failed` / `unknown`.
Таймаут/потеря соединения с неизвестным исходом не вызывает автоматического
повтора и не объявляется бесплатной операцией. Ожидаемый вес `running`/`unknown`
показан отдельно от успешного расхода; это ещё не атомарный резерв квоты.

Период, грант и вес фиксируются при старте. Завершение после границы месяца
относят к исходному периоду. Подтверждённый личный аккаунт получает один грант
Демо; платный период не использует и не увеличивает его. При создании агентства
владельцем сохраняются подписка, период и расход, а личный грант с прежним ID
и расходом остаётся в личной области. Вступление сотрудника в чужую команду
не переносит личную подписку или бюджет.

Исторические `AIContent` не тарифицируются задним числом. Наблюдаемые кредиты
не записываются в финансовые счётчики периода/гранта: сервис правил складывает
их с журналом. При будущей смене механизма нельзя считать эти значения дважды.
Генерации до подтверждения email видны в журнале, но не уменьшают ещё не выданный
грант. При неизвестных условиях `credit_cost_unknown` показывает проблему:
технический нулевой вес не означает утверждённую бесплатную цену.

UUID защищает повторную запись одной внутренней операции и её завершения.
Стабильный ключ повторного HTTP-запроса ещё не передаётся интерфейсом; новый
запрос генерации сейчас считается новой операцией. Ограничение параллелизма,
дедупликация запросов и атомарный резерв потребуются перед платным запуском.
Будущие пути ИИ должны использовать обёртку учёта, не вызывать `AIService`
напрямую.

## Установка и наблюдение

Перед миграциями резервируйте БД и media. Для текущих SQLite и локальных файлов:

```bash
python manage.py backup_crm --output-dir "$PWD/.crm-backups"
python manage.py migrate
python manage.py reconcile_billing_usage
python manage.py billing_usage_report
```

Миграции `billing.0003`–`0005` добавляют журнал, реестр и связь с результатами.
Полная сверка создаёт недостающие личные/командные счета и гранты ранее
подтверждённых пользователей. Она записывает базовое состояние и коррекции,
не выдаёт платные подписки, не меняет CRM и не удаляет файлы. Повтор без новых
изменений не создаёт новых проводок. Приглашения учитываются на текущую дату:
истёкшие перестают занимать место даже без удаления записи.

```bash
python manage.py reconcile_billing_usage --account-id 1
python manage.py reconcile_billing_usage --counts-only
python manage.py billing_usage_report --account-id 1
```

`--counts-only` сверяет записи и известный реестр, но не проверяет физические
файлы и не заменяет полную сверку. Отчёт только читает БД: показывает текущие
ресурсы, лимиты, ИИ-расход/ожидающий расход, полноту/время инвентаризации,
неизвестные операции/usage и число предполагаемых тарифных отказов. Состояние
тарифа и `allowed=false` — диагностические результаты, не фактическая блокировка.

Старые `running` явно переводятся в `unknown`:

```bash
python manage.py review_stale_billing_operations --age-minutes 15
```

Если результаты сохранены, но завершение учёта не записалось, оператор может
восстановить расход по `UsageResult`, без нового запроса к модели:

```bash
python manage.py review_stale_billing_operations --age-minutes 15 --recover-saved
```

Без достоверной связи с сохранёнными результатами операция остаётся неизвестной
до отдельного разбора. Нет автоматических повторов, возвратов или списания по
догадке. Периодический запуск команд на сервере пока не настроен; на пилоте
проверяйте журнал и выполняйте сверку вручную, а расписание согласуйте отдельно.

Ошибка наблюдения логируется как `billing.observation` с типом исключения,
без его текста/секретов. Отдельная транзакция учёта не отменяет CRM-действие.
Цена такого режима — возможные пробелы в журнале: ресурсы восстанавливаются
сверкой, ИИ — только по достоверным связям, иначе требуется разбор оператора.
После `BILLING_SHADOW_ENABLED=False` и перед включением блокировок обязательна
полная сверка и проверка незавершённых операций.

## Проверка и следующий этап

```bash
python manage.py test billing
python manage.py test
python manage.py makemigrations --check --dry-run
python manage.py check
```

Тесты API используют имитацию, не платные запросы. SQLite-тесты проверяют
сценарии и повторяемость журнала, но не доказывают конкурентную защиту PostgreSQL.
Прямой SQL может обходить семантическую неизменяемость `save()`; изменения
финансовой истории должны выполняться только доверенными сервисами.

Тариф, состояние доступа, даты периодов, ресурсы и ИИ-бюджет показаны
[в разделе «Тариф и расход»](billing-interface.md).

Далее по текущему состоянию: проверяем конкуренцию на production-БД и все пути
записи, затем отдельно включаем тарифные ограничения. Ограничение глобального бюджета провайдера,
ценовой расчёт, платежи, возвраты и автопродление ещё не реализованы.
