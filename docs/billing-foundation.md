# Тарифный слой: модели и сервис правил

Этап 2, 28 сентября 2026 года. Основа — [спецификация BP-0.1](billing-policy.md).

Подготовлен внутренний слой счетов и решений. На третьем этапе подключён
[учёт без блокировок](billing-metering.md): изменения ресурсов и ИИ-операции
записываются в журнал. Он **ещё не ограничивает действия в кабинете**,
не отключает публичные лендинги и не делает платежей, автосписаний или отправки
финансовых счетов. Сам учёт не запускает дополнительных запросов к модели.

## Модели

| Модель | Назначение |
| --- | --- |
| `BillingAccount` | Личный или командный тарифный счёт, отдельный плательщик |
| `Plan` | Идентичность тарифа: Демо, Стандарт, Бизнес |
| `PlanVersion` | Неизменяемая версия лимитов, функций, весов ИИ и будущей цены |
| `Subscription` | Привязка счёта к календарю, флаги приостановки/отмены и запланированная версия |
| `BillingPeriod` | Конечный срок предоставленного доступа, снимок условий и месячный бюджет ИИ |
| `DemoCreditGrant` | Один грант на пользователя за всё время, отдельный от месячных бюджетов |

`BillingAccount` — не финансовый счёт на оплату. В нём ровно одна область:
`personal_user` **или** `agency`. Плательщик может отличаться от владельца и не
получает доступ к CRM. Существующие личные и командные записи не перемещаются
при создании тарифного счёта.

Пользовательские/командные счета создаются внутренним сервисом при наблюдении
изменений или явной инвентаризации. Чтение отчёта не создаёт счета. Платные
подписки старым кабинетам массово не выдаются; условия пилота назначает оператор.

## Каталог и миграции

`billing.0001_initial` добавляет шесть таблиц, внешние ключи и ограничения БД.
`billing.0002_seed_plan_catalog` создаёт версии `v1` по BP-0.1; повторный запуск
не размножает каталог. Значения миграции зафиксированы, а не импортируются из
изменяемого словаря в приложении.

- Демо: 2 объекта / 1 лендинг / 1 место / 200 МиБ / 5 разовых ИИ-кредитов.
- Стандарт: 20 / 10 / 1 / 2 ГиБ / 100 кредитов за период.
- Бизнес: 100 / 50 / 5 / 10 ГиБ / 500 общих кредитов за период.

Технические потолки всех карточек, включая архив, — 50 / 1000 / 5000.
Они остаются предварительными до пилота. Стоимости операций: короткий текст,
улучшение и ответ — 1; описание — 2; комплект — 3; лендинг — 5; локальный аудит — 0.

Цена Демо равна нулю. Цены Стандарта/Бизнеса — `NULL`, валюта пустая: это
**не нулевая платная цена**. `available=True` разрешает внутреннее назначение
пилота, но не продажу. `sale_ready` становится истинным только у доступной
платной версии с положительной ценой и трёхбуквенным кодом валюты. Утверждение
цены требует новой версии; интерфейс покупки пока отсутствует.

Перед применением:

```bash
python manage.py backup_crm --output-dir "$PWD/.crm-backups"
python manage.py migrate
python manage.py check
```

Команда резервирования поддерживает SQLite и локальные media; для другого
production-хранилища нужны отдельные средства резервирования.

## Явные сервисы

`AccountService.ensure_personal(user)` и `ensure_agency(agency)` повторяемо
создают счёт без переноса CRM. `for_resource(resource)` только ищет счёт по
самой записи; если он ещё не создан, возвращается ошибка отсутствия записи.
`matches(account, resource)` позволяет отсеять чужое пространство.

Для объектов/клиентов/сделок/задач/показов используется область записи; для
заявок, фотографий и ИИ-текстов — область их объекта. Приглашения и членство
относятся к счёту агентства. Нельзя использовать объединённый queryset кабинета
или личный тариф сотрудника для списания общих ресурсов команды.

`SubscriptionService.grant_period(...)` — внутреннее назначение ограниченного
по времени доступа. Нужны оператор с разрешением `billing.add_billingperiod`,
основание, UUID операции, версия тарифа и дата начала с часовым поясом.
Допустимы основания `pilot` и `manual`: это **не подтверждение оплаты**.
Обычный пользователь не может назначить себе тариф.

Одинаковый UUID с одинаковыми параметрами возвращает исходный период и не
сбрасывает расход. Повтор с другими параметрами отклоняется. Неотменённые
периоды одной подписки не пересекаются; соседние интервалы допустимы.

Пример для внутреннего операторского скрипта (не публичного view):

```python
import uuid
from datetime import datetime, timezone
from billing.models import Plan
from billing.services import AccountService, SubscriptionService, current_plan_version

# user и operator — уже проверенные пользователи приложения.
account = AccountService.ensure_personal(user)
operation_id = uuid.uuid4()  # Сохранить и повторно использовать при повторе этой операции.
period = SubscriptionService.grant_period(
    account=account,
    plan_version=current_plan_version(Plan.Code.STANDARD),
    actor=operator,
    reason="Пилотный доступ по согласованию",
    request_key=operation_id,
    starts_at=datetime(2026, 10, 1, tzinfo=timezone.utc),
)
```

`ensure_demo_grant(user)` явно выдаёт грант после подтверждения email. Повтор
возвращает исходный грант, даже после смены email/тарифа: он связан с личностью
пользователя, а не очередным расчётным месяцем. В платном периоде этот остаток
не добавляется к месячной квоте; после возвращения в Демо остаётся прежний
неизрасходованный баланс. Личный грант не оплачивает командные генерации.
При включённом учёте сохранение подтверждённого профиля выдаёт грант после
коммита. Для ранее подтверждённых аккаунтов грант создаёт сверка или первое
наблюдаемое ИИ-действие. Повторный вызов не увеличивает бюджет.

## Единый сервис решений

`PolicyService.evaluate(account, actor, operation, ...)` возвращает
`PolicyDecision`: `allowed`, стабильный `code`, пояснение, тариф/режим, лимит,
расход, необходимый прирост и стоимость ИИ. Это результат проверки, не
разрешение пропускать обычную проверку CSRF/формы/прав доступа к записи.

Пример проверки без изменений в БД:

```python
from billing.rules import Operation, PolicyService

decision = PolicyService.evaluate(
    account,
    user,
    Operation.CREATE_PROPERTY,
)
print(decision.allowed, decision.code, decision.limit, decision.used)
```

Все операции перечислены в `Operation`: чтение/CSV, работа с CRM, создание и
восстановление объектов, публикация/публичный лендинг, файлы, ИИ, XML, агентство
и сотрудники. Расчёт не меняет записи, членство, бюджеты или публикации.
Плательщик/оператор не получает CRM-права вместо владельца; права сотрудников
проверяются независимо от тарифа. Принятие приглашения заменяет зарезервированное
место, а не требует второго места, но повторно проверяет общую вместимость.

`collect_usage(account)` считает записи конкретного пространства: все
неархивные объекты (включая черновики, проданные, сданные и демо), все карточки,
намерения публикации, участников и действующие приглашения. Архив исключён
из активной квоты. Истёкшие/принятые приглашения не занимают дополнительный резерв.

Объём файлов берётся из серверной инвентаризации. До полной сверки ссылок или
при неизвестном размере он возвращается как `None`: это **не ноль байтов**.
Без проверенного размера решение загрузки — `usage_unknown`. Сверенный серверный
`UsageSnapshot` может содержать байты и резервы; нельзя принимать его от клиента.
Статические лимиты безопасности отдельных загрузок в `properties` сохраняются.
Настоящие атомарные резервы пока не подключены.

Бюджеты ИИ подготовлены в периоде/гранте: выделено, использовано, зарезервировано.
Сервис учитывает исходные счётчики и наблюдаемый журнал при проверке. Успешный
сохранённый результат добавляет расход в журнал, но не изменяет финансовые
счётчики периода/гранта. Незавершённые/неизвестные операции показаны как ожидаемый
расход, не настоящий резерв. Расход не восстанавливается из количества
`AIContent`: комплект остаётся одной операцией. Исторические тексты не
тарифицируются задним числом. Провайдерские токены сохраняются отдельно от
условных ИИ-кредитов; расчёта денежной себестоимости пока нет.

При создании агентства владельцем `convert_founder_account(...)` сохраняет
идентичность его счета, подписку, период и журнал за командным пространством.
Для новой личной области создаётся отдельный счёт; личный грант сохраняет свой
ID и накопленный расход. Вступление сотрудника в чужую команду ничего не переносит.

## Даты и сохранность

Даты приводятся к UTC; интервалы — `[starts_at, ends_at)`. Календарные границы
вычисляются от исходной привязки: 31 января → 28 февраля → 31 марта. Будущий
период не меняет текущий расход и становится доступен только с даты начала.

Оператор передаёт **начало расчётного периода**, не время поступления оплаты.
При продлении в льготный срок начало нового периода — прежнее окончание.
После окончания льготного срока новый сегмент получает новую исходную привязку.
Платёжный адаптер, который определит эти даты по проверенному платежу, ещё не создан.

Режим определяется по текущей дате, без зависимости от фонового задания:

- `active` — действующий конечный период и его снимок условий.
- `grace` — 7 × 24 часа после окончания, существующая CRM и доступные страницы
  работают; рост ресурсов, генерации, XML и новые приглашения запрещены правилами.
- `demo` / `restricted` — начальное Демо / возврат к Демо после периода.
  Избыток сохраняется; сотрудники команды имеют чтение, владелец — доступ
  в пределах личного тарифа. Никто автоматически не удаляется/архивируется.
- `suspended` — ручная приостановка с основанием; чтение и CSV сохраняются.

Если прежних публикаций больше новой квоты и набор доступных страниц не выбран,
проверка публичного доступа возвращает `landing_selection_required`. Сейчас
это только решение сервиса: интерфейс выбора и подключение к GET/POST лендинга
будут отдельным этапом. URL, настройки и CRM не удаляются.

Версии тарифов, снимки и исходный бюджет периода защищены от изменения через
обычный `save()`. Изменение сетки требует новой версии. Аннулирование периода
требует причины и необратимо; при ошибке создаётся новый период. Администрация
показывает счета/подписки/периоды/гранты только для чтения и не удаляет историю.

## Что ещё не реализовано

- Атомарные резервы и защита от повторов. Тариф, даты, расход ресурсов,
  ИИ-бюджет и предупреждения уже доступны [в кабинете](billing-interface.md).
- Настоящие атомарные резервы и единый шлюз записи ресурсов.
- Дедупликация пользовательских ИИ-запросов по стабильному HTTP-ключу.
- Автоматическое применение запланированного тарифа/отмены: поля пока метаданные.
- Пропорциональные доплаты/кредиты повышения, заказы, платежи, возвраты и вебхуки.
- Подключение проверок ко всем пользовательским, массовым, административным
  и фоновым путям; изменение небезопасного GET создания черновика на POST.

Неизменяемость на уровне `save()` не защищает от прямого SQL,
`QuerySet.update()`/`bulk_create()`. Ограничения БД защищают форму счёта,
внешние ключи, длительность и отсутствие перерасхода бюджета; семантическую
неизменяемость и непересечение обеспечивает доверенный сервис. Все будущие
изменяющие ресурсы пути должны соблюдать единую транзакционную дисциплину.

Назначение периодов блокирует общий счёт. Для production конкурентные сценарии
нужно проверять на PostgreSQL: SQLite-тесты не доказывают защиту от одновременных
загрузок/ИИ/созданий. Одна предварительная проверка без резерва ещё не является
защитой от гонок.

Проверка этапа:

```bash
python manage.py test billing
python manage.py test
python manage.py makemigrations --check --dry-run
python manage.py check
```
