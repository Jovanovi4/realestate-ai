# Подготовка тарифных ограничений

29 сентября 2026 года. Платежи не подключены. Флаг `BILLING_ENFORCEMENT_ENABLED`
по умолчанию выключен, поэтому текущие пользователи продолжают работать в
наблюдательном режиме. Не включайте его на рабочей базе до выполнения проверок
ниже.

## Что уже проходит через серверное решение

- Создание объекта и демо-объекта, восстановление из архива (обе формы URL),
  публикация лендинга, загрузка фото и логотипа, приглашение и принятие
  приглашения проверяются под блокировкой счёта. Для совместного создания
  объекта с лендингом/логотипом проверяются все соответствующие лимиты.
- ИИ-кредиты резервируются до обращения к провайдеру. При отказе запрос к
  провайдеру не отправляется, операция не создаётся. Повтор с тем же ключом
  возвращает сохранённый результат по правилам идемпотентности.
- Архивирование, снятие лендинга с публикации, изменение объекта и галереи,
  операции с клиентами, заявками, сделками, задачами, показами и сохранёнными
  ИИ-текстами, смена роли/исключение сотрудника и назначение ответственного
  проверяют состояние доступа. При отказе данные сохраняются без изменений,
  интерфейс показывает причину. Просмотр и выгрузка CSV сохраняются.
- Публичный лендинг проверяется и при GET, и при POST. Посетитель видит
  нейтральную страницу 503 без подробностей о счёте; предпросмотр владельца
  доступен. Скачивание XML проверяет право на экспорт для каждого пространства
  включённых объектов.
- При включённом флаге CRM-записи в Django admin доступны только для просмотра;
  обычные формы и массовые действия больше не обходят кабинетные проверки.
  Записи счетов и периодов остаются отдельным операторским процессом.

Флаг включается только после успешного полного аудита и тестов. Ручное
включение сейчас преждевременно: это уже реальная блокировка действий и
публичных страниц.

## Что осталось до включения

1. Провести гонки на *отдельной пустой* PostgreSQL test database с теми же
   версиями сервера и драйвера, что в рабочем окружении. SQLite не проверяет
   семантику `SELECT FOR UPDATE`. Два теста в `billing/test_postgres_contention.py`
   проверяют последнюю ячейку объекта и последние ИИ-кредиты. На SQLite они
   корректно пропускаются.
2. Перед включением на любом окружении выполнить сверку файлов и расхода,
   разобрать неизвестные размеры и незавершённые ИИ-операции, проверить
   содержимое активных счетов и составить план для уже превышенных лимитов.
   После этого проверить полный набор HTTP-сценариев, включая публичную
   отправку заявки, и включить флаг сначала на тестовом окружении.

Результат локальной сверки от 29 сентября 2026 года: [отчёт по счетам и
файлам](billing-audit-2026-09-29.md).

Редактирование своего профиля остаётся доступно для связи и восстановления
аккаунта. Фото профиля по BP-0.1 — личный технический ресурс с отдельной
проверкой размера, вне командной квоты. Аудит известных HTTP-путей создания
квотируемых ресурсов завершён; при добавлении импорта, management-команд или
интеграций необходимо провести их через резервный шлюз. Прямой ORM-доступ
оператора не является защищённым HTTP-путём и требует отдельной процедуры.

Проверки без браузера:

```bash
venv/bin/python manage.py test billing properties
venv/bin/python manage.py check
venv/bin/python manage.py makemigrations --check --dry-run
```

Для проверки PostgreSQL задайте отдельный `DATABASE_URL`, направленный на
временную тестовую базу, и запускайте только на ней:

```bash
venv/bin/python manage.py test billing.test_postgres_contention --verbosity 2
```

Тестовый раннер Django создаёт свою базу с префиксом `test_`; пользователь БД
должен иметь разрешение на это. Не используйте URL рабочей базы, если не
проверены её права и изоляция.
