# RealEstate AI

Для пилотного VPS с Docker Compose: [порядок развёртывания](docs/docker-pilot.md).

Django-сервис для риелторов: ведение объектов недвижимости, лендинги, заявки, ИИ-тексты и ручная выгрузка XML для Avito.

## Возможности

- Регистрация и вход по телефону.
- Карточки квартир, домов, дач, участков и коммерческих объектов; [типы и правила цены для коммерческих помещений](docs/commercial-property-scope.md).
- Фотогалерея: главное фото, удаление и изменение порядка.
- Три адаптивных шаблона публичных лендингов с SEO-настройками.
- Заявки с лендингов и личный кабинет риелтора.
- [Отношения с клиентом](docs/client-relationship-status.md) отдельно от этапов сделок по паре «клиент — объект»; у сделок есть задачи, показы и ожидаемая комиссия.
- Агентство: общая база, роли сотрудников, назначение заявок и журнал изменений.
- [Аналитика CRM](docs/crm-analytics-metrics.md): отдельный экран со сводкой заявок, первого ответа, задач, источников и текущей воронки для личного пространства и команды.
- [Входящие обращения](docs/inbound-intake.md): публичные формы, опциональная почтовая очередь и управляемое объединение контактов.
- ИИ-помощник через OpenAI API с историей генераций; для локальных тестов доступна Ollama.
- Ручная выгрузка отмеченных объектов в XML для Avito.

Сделка создаётся вручную из карточки заявки, клиента или объекта после квалификации обращения. Старые заявки не превращаются в сделки автоматически: это позволило сохранить их исходный смысл и не заполнить воронку неподтверждёнными переговорами. Для одного клиента и объекта может быть только одна активная сделка; после закрытия можно создать новую.

## Рабочий день риелтора

Раздел «Сегодня» собирает задачи и показы владельца кабинета, выделяет просроченные дела и позволяет отметить задачу выполненной. Старые напоминания по клиентам сохраняются как задачи. У одной сделки может быть несколько показов; после проведения нужно записать итог. Прежние поля сделки «следующее действие» и «дата показа» переносятся в задачи и показы миграцией `0035_workday`.
Граница календарного дня в CRM и аналитике определяется общим часовым поясом Django: задайте `TIME_ZONE` в окружении для своего рынка (по умолчанию `Europe/Moscow`).

Просрочка видна в кабинете сразу. Для внешних уведомлений настройте email и/или Telegram так же, как для заявок, и добавьте в расписание хостинга команду:

```bash
python manage.py send_overdue_tasks
```

Для проверки без отправки используйте `python manage.py send_overdue_tasks --dry-run`. Команда отправляет одно сводное уведомление о просроченных задачах и повторно их не рассылает; после переноса срока задача снова сможет попасть в уведомление. Без запуска команды по расписанию внешние уведомления не отправляются.

## Агентство и общая база

На странице «Команда» владелец создаёт агентство. Это действие переводит его текущие личные объекты, клиентов, обращения собственников, сделки, задачи и показы в общую базу. Публичные URL лендингов и существующие заявки сохраняются. Создание агентства нужно подтверждать осознанно: подключённые сотрудники получат доступ к перенесённым контактам и истории CRM. Личные данные приглашённого сотрудника в общую базу автоматически **не** переносятся. Правила ролей и будущего закрытия команды — в [политике командного пространства](docs/team-workspace-policy.md).

Владелец приглашает руководителя или риелтора одноразовой ссылкой, действующей 7 дней; приглашение можно отозвать. Руководитель может приглашать только риелторов. Все участники видят общую базу и могут вести её записи; владелец и руководитель дополнительно назначают ответственного за заявку, архивируют и восстанавливают общие объекты. Заявки можно перенести в архив, а клиентов со связанной CRM-историей нельзя удалить каскадом. Только владелец меняет роли и исключает сотрудников. При исключении общие записи и назначения бывшего сотрудника передаются владельцу. Раздел «Мои заявки» фильтрует обращения по ответственному; раздел «Сегодня» остаётся личным для каждого сотрудника.

Журнал фиксирует создание, изменение, архивирование, восстановление и разрешённое удаление записей, имя вошедшего пользователя и названия изменённых полей без копирования телефонов или содержимого полей. Публичные заявки отмечаются как действие посетителя/системы. История до включения журнала не восстанавливается. Массовые операции в приложении выполняются с записью истории; прямые изменения в БД и сторонние скрипты через `QuerySet.update()` в журнал не попадут.

Миграции `0036`–`0037` создают модель агентства и назначают существующим заявкам ответственного владельца объекта. Перед развёртыванием сделайте резервную копию БД и выполните `python manage.py migrate`. Тарифные ограничения и платежи пока не подключены: экран команды доступен без проверки Бизнес-тарифа. Перед коммерческим запуском проверьте документы по персональным данным для командного доступа.

## Тарифный слой — учёт и подготовка ограничений

В [спецификации BP-0.1](docs/billing-policy.md) зафиксированы правила учёта
личных/командных ресурсов, предварительные лимиты Демо / Стандарт / Бизнес,
ИИ-кредиты, расчётные периоды и сохранность данных при неоплате.
Приложение `billing` содержит личные/командные счета, версии тарифов, подписки,
расчётные периоды и разовый грант Демо. Миграции добавляют каталог трёх тарифов,
но не назначают платные подписки существующим пользователям. Сервис правил
проверяет возможность действий, а журнал фиксирует изменения ресурсов,
ИИ-операции и предполагаемые отказы в наблюдательном режиме.

**Тарифные блокировки и платежи по умолчанию не включены**, цены не установлены. При
`BILLING_SHADOW_ENABLED=True` учитываются объекты, публикации, места команды,
сохранённые фото/логотипы, ИИ-кредиты и доступные метаданные токенов провайдера.
При выключенном флаге ограничений превышение не мешает работе;
исторические ИИ-тексты не списываются задним числом.
Провайдер и модель ИИ не переключаются.

Перед миграциями сделайте резервную копию. Затем выполните первоначальную
сверку; повтор безопасен и не удаляет файлы:

```bash
python manage.py migrate
python manage.py reconcile_billing_usage
python manage.py billing_usage_report
```

Модели и сервис правил описаны [здесь](docs/billing-foundation.md), устройство
журнала, сверка файлов и восстановление незавершённых операций —
[в инструкции по учёту](docs/billing-metering.md). В личном кабинете доступен
раздел «Тариф и расход»: текущий тариф, состояние доступа, даты периодов,
объекты, лендинги, рабочие места, объём файлов и остаток ИИ-кредитов показаны
отдельно для личной области и команды. Ожидаемый расход незавершённых генераций
показан отдельно; неизвестный объём файлов не превращается в ноль. Открытие
страницы не создаёт счета или кредиты. Подробнее —
[в описании интерфейса](docs/billing-interface.md). Атомарные резервы и защита
от повторных запросов описаны [отдельно](docs/billing-reservations.md).
Проверки лимитов за флагом `BILLING_ENFORCEMENT_ENABLED` и условия их включения
описаны [в плане внедрения](docs/billing-enforcement.md). На локальной SQLite
флаг остаётся выключенным до проверки конкурирующих запросов на PostgreSQL и
закрытия оставшихся путей записи.

## Обработка входящих заявок

В разделе «Заявки» доступны фильтры по статусу и ответственному. У каждой
заявки видны источник, время поступления, ответственный, квалификация, первый
контакт и следующий шаг со сроком. Первый ответ требуется в течение 30 минут
после поступления: перенос следующего шага не переносит этот срок. Первый
контакт фиксируется в карточке заявки один раз вместе со способом связи,
результатом квалификации и следующим действием; событие попадает в историю
клиента. Просроченные действия ответственного также видны в «Моём дне».
Предупреждения отображаются в кабинете; уведомления о просроченных задачах
требуют настройки каналов и запуска существующей команды `send_overdue_tasks`.

Активное следующее действие заявки связано с одной задачей CRM. В карточке
можно завершить её, записать итог и назначить новую задачу со сроком; история
остаётся в заявке и у связанного клиента. Изменение срока или ответственного
обновляет текущую задачу, архивирование отменяет её. В «Моём дне» связанная
задача показывается один раз, в блоке заявок. Миграция `0041` создаёт задачи
для существующих активных заявок, не отправляя задним числом уведомления о
прошлых сроках.

Запрос на подбор можно добавить вручную в разделе «Заявки» без предварительного
создания объекта. При создании выбираются источник, личное или командное
пространство и ответственный; пожелания сохраняются в заявке, а срок первого
ответа наступает через 30 минут. После разговора объект привязывается во
вкладке «Об обращении», затем целевую заявку можно перевести в сделку.
Миграция `0060` переносит область доступа старых заявок с объекта на саму
заявку, сохраняя прежние связи, историю и источники лендинга и Telegram.

После первого контакта и квалификации целевую заявку можно перевести в новую
или существующую сделку по тому же клиенту и объекту. Текущее действие заявки
при этом закрывается и переносится в задачу сделки; повторная отправка не
создаёт вторую задачу. Заявку также можно закрыть без сделки с обязательной
причиной и при необходимости возобновить. Итог и история видны в карточке,
завершённые заявки не попадают в «Мой день» и счётчики ожидающих ответа.
Миграция `0042` отмечает связанные со сделками старые заявки как переведённые
и закрывает их прежние задачи без создания новых задним числом.

Перед применением миграции `0040` сделайте резервную копию. Для старых заявок
срок первого ответа и исходного следующего действия вычисляется от времени
поступления; старые обращения без отмеченного контакта могут сразу появиться
в разделе «Мой день» как просроченные.

## Импорт клиентов

В разделе «Клиенты» доступен импорт CSV. Нужны столбцы «Имя» и «Телефон»;
поддерживаются формат собственного экспорта, UTF-8 или Windows-1251 и разделители
«,» или «;». Можно передать статус, источник, бюджет, район, удобное время и
комментарий. Новый экспорт использует столбец «Отношения»; старые файлы со
столбцом «Статус» и прежними этапами также принимаются. Лимит файла — 1 МБ и
1000 контактов.

Импорт создаёт только карточки клиентов в текущем личном или командном
пространстве. Телефоны нормализуются; совпадения в доступной базе и повторные
строки пропускаются, существующие карточки не перезаписываются. Если в CSV есть
ошибки, импорт не сохраняет ни одного контакта. Заявки, задачи, сделки и даты
их создания из CSV не восстанавливаются.

## Архив CRM, сроки хранения и резервные копии

Удаление объекта заменено обратимым архивированием с сохранением фотографий,
заявок, сделок, показов и задач. Архив открывается в разделе «Объекты».
Восстановление не публикует лендинг и не включает экспорт автоматически.
Удаление заявки также переносит её в архив. Клиенты со связанной CRM-историей
защищены от каскадного удаления. Перед применением миграции `0039` сделайте копию.

Срок пересмотра архивной истории — **3 календарных месяца**. Сейчас команды
только отчётные: автоматическое удаление CRM и старых копий отключено.

```bash
python manage.py backup_crm --output-dir "$PWD/.crm-backups"
python manage.py verify_crm_backup --latest --output-dir "$PWD/.crm-backups"
python manage.py crm_retention_report
```

Резервирование поддерживает SQLite + локальные media и проверяет настоящее
восстановление в отдельную временную папку. Для PostgreSQL/облачного storage
нужна соответствующая инфраструктурная схема. Linux systemd-шаблоны ежедневного
запуска подготовлены, но **не включены**; сервер, внешнее хранение копий и
аварийные уведомления ещё нужно настроить.

Подробности, ограничения и порядок восстановления —
[в инструкции](docs/crm-history-and-backups.md).

## Локальный запуск

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
python manage.py migrate
python manage.py runserver
```

Откройте `http://127.0.0.1:8000/`.

## Настройки окружения

Переменные приведены в [.env.example](.env.example). Их нужно задать в терминале или в настройках хостинга; реальный файл с ключами не добавляйте в Git.

По умолчанию ИИ использует OpenAI API. Для генерации задайте ключ в приватном
окружении; не добавляйте его в Git:

```bash
export AI_PROVIDER=openai
export OPENAI_MODEL=gpt-6-luna
export OPENAI_REASONING_EFFORT=none
printf 'OpenAI API key: '
read -rs OPENAI_API_KEY
printf '\n'
export OPENAI_API_KEY
```

Для локальных тестов без API можно задать `AI_PROVIDER=ollama` и запустить Ollama
с моделью из `OLLAMA_MODEL`. Подписка ChatGPT не заменяет доступ и ключ к OpenAI API.

## Уведомления о новых заявках

После публикации лендинга новая заявка всегда сохраняется в CRM. Дополнительно
можно включить уведомления на email и в Telegram — ошибка доставки не помешает
клиенту отправить форму.

1. В настройках окружения включите `EMAIL_NOTIFICATIONS_ENABLED=True` и
   укажите SMTP-параметры вместе с `DEFAULT_FROM_EMAIL`. Письмо уйдёт на email,
   указанный в профиле риелтора.
2. Создайте Telegram-бота через BotFather, сохраните его токен только в
   `TELEGRAM_BOT_TOKEN` на хостинге и включите
   `TELEGRAM_NOTIFICATIONS_ENABLED=True`.
3. Риелтор должен открыть диалог с ботом и отправить ему `/start`, затем указать
   свой приватный `chat_id` в личном кабинете. Это значение не публикуется на
   лендингах.
4. После изменения модели выполните `python manage.py migrate` при следующем
   развёртывании.

## Публичный Telegram-бот для объявлений и заявок

Это отдельный бот для покупателей. Служебные уведомления риелтору продолжают
использовать `TELEGRAM_BOT_TOKEN`; не подставляйте этот токен в публичный бот.

1. Создайте отдельного бота в BotFather. На HTTPS-хостинге задайте
   `TELEGRAM_PUBLIC_BOT_TOKEN`, `TELEGRAM_PUBLIC_BOT_USERNAME` (без `@`),
   случайный `TELEGRAM_PUBLIC_WEBHOOK_SECRET` и
   `ACCOUNT_PUBLIC_BASE_URL=https://...`. Включите `TELEGRAM_PUBLIC_ENABLED=True`
   после развёртывания и миграций.
2. После развёртывания выполните
   `python manage.py register_telegram_public_webhook`. Команда вызывает метод
   Telegram `setWebhook` с HTTPS-адресом `/telegram/public/webhook/`, секретом
   из окружения и обновлениями `message`/`callback_query`. Токен и секрет не
   помещайте в URL вебхука или логи приложения.
3. Запускайте `python manage.py send_telegram_publications --limit 20` для
   отправки очереди. Команда `--dry-run` показывает очередь без отправки.
   Ответы бота на входящие сообщения и уведомления о новых заявках теперь
   сохраняются в отдельной очереди: `python manage.py send_outbound_messages`
   повторяет их при временном сбое. В Docker-пилоте эта команда работает
   постоянно в сервисе `outbound`; на других стендах запустите её по расписанию.
   На PythonAnywhere Free без фонового процесса повтор запускается вручную из
   Bash-консоли; до такого запуска неотправленные сообщения остаются в базе.
   На PythonAnywhere Free для первого теста запускайте её вручную в Bash-консоли:
   у новых бесплатных аккаунтов Scheduled Tasks недоступны, у старых — не чаще
   раза в день. На платном аккаунте доступны почасовые задачи; для отправки
   чаще потребуется отдельный постоянный процесс. Не запускайте два
   экземпляра команды одновременно. Фото должны открываться по публичному
   HTTPS-адресу из `ACCOUNT_PUBLIC_BASE_URL`.
   [Ограничения PythonAnywhere](https://help.pythonanywhere.com/pages/ScheduledTasks/).
   Переменные бота должны быть доступны как WSGI-приложению, так и Bash-командам:
   значения, заданные только в WSGI-файле, не попадают в консоль.
4. Постоянные ссылки на личную и командную ленты находятся в разделе
   «Интеграции → Telegram». Они работают и до первой публикации: клиент
   подписывается сейчас и получит следующие объявления после отправки очереди.
   Там же видны опубликованные объекты, число активных подписчиков и состояние
   последней рассылки каждого объекта: очередь, отправка, ошибка или отсутствие
   получателей. Публикация и снятие объявления доступны в карточке объекта.
   Ссылка на ленту объекта также видна в его карточке на вкладке «Публикация».
   В карточке реального объекта откройте «Публикация» → «Объявление в боте».
   Статус объекта должен быть «Опубликован», «Свободен» или «На показах».
   После публикации можно поделиться ссылкой на конкретное объявление: она открывает бота,
   подписывает покупателя на новые объекты этого личного или командного
   пространства и показывает выбранный объект. Новые объекты рассылаются
   только уже подписавшимся покупателям. `/subscriptions` показывает активные
   ленты и кнопки отключения каждой. `/stop` отключает единственную ленту
   сразу, а при нескольких предлагает выбрать ленту или отключить все.
   `/stop all` отключает все ленты явно. Неотправленные объявления отключённой
   ленты снимаются с очереди; повторная подписка не возобновляет старую очередь.
   Вход по постоянной ссылке показывает последнее доступное объявление ленты,
   если оно есть. Клиент подписывается только на ленту из открытой ссылки.
   Обычный `/start` подписывает автоматически, только если у бота ровно одно
   пространство с опубликованными объявлениями; при нескольких пространствах
   нужна ссылка на ленту или конкретный объект.

Нажатие «Откликнуться» запрашивает телефон. После его отправки покупатель
отдельно подтверждает согласие и отправку заявки. Только тогда создаются
клиент (либо используется существующий), заявка с источником «Telegram-бот» и
задача связаться в течение 30 минут. Повторные события Telegram не создают
повторную заявку. Снятые с публикации и архивные объекты больше не принимают
отклики. Ссылка на согласие и политику берётся из `ACCOUNT_PUBLIC_BASE_URL`.

## Защита аккаунтов и восстановление доступа

Вход (включая Django Admin), регистрация, восстановление и подтверждение email
ограничены через cache до выполнения проверки пароля или создания аккаунта.
Превышение лимита возвращает страницу в стиле кабинета, HTTP 429 и `Retry-After`.
При недоступности cache запросы не пропускаются без защиты.

- Вход: до 5 попыток на пару IP–номер, 20 на номер с разных IP и 30 на IP
  за 15 минут. Лимит учитывает все попытки, включая успешные, и не создаёт
  постоянной блокировки аккаунта.
- Регистрация: до 5 попыток на IP и 3 на номер за час.
- Восстановление: до 10 запросов на IP и 3 на email за час.
- Запрос подтверждения email: до 10 на IP и 3 на аккаунт за час.
- Отправка форм по ссылкам подтверждения/сброса: до 20 на IP за 15 минут.

Настройки заданы в `AUTH_RATE_LIMITS`. Ключи cache содержат HMAC-отпечатки,
а не телефоны, email или IP в открытом виде. В production необходим общий
Redis cache для всех процессов: задайте
`CACHE_BACKEND=django.core.cache.backends.redis.RedisCache` и
`CACHE_LOCATION=redis://…`. Локальный memory cache подходит только для разработки
и не даёт общего лимита между процессами. Не выставляйте Redis в интернет.
`AUTH_TRUST_X_FORWARDED_FOR=True` разрешён только за доверенным proxy, который
заменяет этот заголовок, а не передаёт произвольное значение посетителя.

Для восстановления пользователь заранее сохраняет email в профиле, нажимает
«Подтвердить email», вводит текущий пароль и подтверждает адрес по ссылке из
письма. Простое открытие ссылки не меняет данные; требуется кнопка подтверждения.
Старые email **не** считаются подтверждёнными автоматически. Подтверждение
телефона пока не реализовано: номер по-прежнему является только логином.

На странице входа есть «Забыли пароль?». Для запроса нужны телефон аккаунта и
его подтверждённый email. Ответ одинаков для существующего, неподтверждённого
и неизвестного аккаунта; отправка SMTP не выполняется в HTTP-запросе. Ссылки
действуют 1 час, одноразовые, не выполняют автоматический вход. Смена email
снимает подтверждение и аннулирует старые ссылки; смена пароля аннулирует
ссылки и существующие сессии. Аккаунты без подтверждённого email восстановить
этим способом нельзя — потребуется отдельная проверка владельца администратором,
а не передача доступа только по названному номеру телефона.

Страницы подтверждения используют `Referrer-Policy: strict-origin` и
`Cache-Control: no-store`: URL с токеном не передаётся в Referer, но origin
сохраняется для CSRF-проверки. Не заменяйте эту политику на `no-referrer`, которая
может превратить Origin отправляемой формы в `null` и вызвать HTTP 403.

Письма хранятся в очереди `AccountEmailRequest`. Для отправки задайте SMTP,
`DEFAULT_FROM_EMAIL` и `ACCOUNT_PUBLIC_BASE_URL=https://ваш-домен`, затем запускайте
**каждую минуту** команду:

```bash
python manage.py send_account_emails
```

Без запуска команды письма останутся в очереди. Это отдельные сервисные письма,
они не зависят от `EMAIL_NOTIFICATIONS_ENABLED`. В локальной проверке можно
использовать console email backend и `ACCOUNT_PUBLIC_BASE_URL=http://127.0.0.1:8000`.
Команда обрабатывает до 100 записей за запуск (`--limit`), делает до 3 попыток
доставки с интервалом не менее 2 минут и отменяет запросы старше часа либо при
изменении состояния аккаунта. SMTP имеет timeout 10 секунд. Для параллельных
worker-команд используйте PostgreSQL; доставка имеет семантику at-least-once:
авария между отправкой SMTP и фиксацией БД может привести к повторному письму.
Токены и пароли в очереди не хранятся.

Перед обновлением выполните `python manage.py migrate` (миграция `0038`).
Настройка SMTP, Redis и расписания выполняется отдельно на выбранном сервере.

CSV клиентов предназначен для просмотра в Excel: ячейки заключаются в кавычки,
кавычки внутри экранируются, потенциальные формулы (включая `+` в телефонах,
пробелы/управляющие символы и полноширинные варианты знаков) получают защитный
префикс табуляции внутри ячейки. Этот символ остаётся в данных при программном
импорте. Универсальной гарантии для всех табличных редакторов и повторного
сохранения CSV нет; для обмена данными нужно учитывать этот формат.

Основание: [OWASP — восстановление пароля](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)
и [CSV injection](https://community.owasp.org/attacks/CSV_Injection).

## Защита публичных форм

Каждая форма заявки уже защищена скрытым honeypot-полем и лимитом отправок с
одного IP: по умолчанию до 8 заявок суммарно и до 3 на один объект за 15 минут.
В production с несколькими процессами настройте общий cache backend, иначе
локальный cache ограничивает попытки только в рамках одного процесса.
`PUBLIC_FORMS_TRUST_X_FORWARDED_FOR=True` включайте только за доверенным
reverse proxy (например, Render), который сам формирует этот заголовок.

Для дополнительной проверки включите Cloudflare Turnstile: создайте widget для
доменов лендингов, сохраните публичный ключ в `TURNSTILE_SITE_KEY`, секретный —
только в `TURNSTILE_SECRET_KEY`, укажите `TURNSTILE_ALLOWED_HOSTNAMES` и задайте
`TURNSTILE_ENABLED=True`. Сервер проверяет каждый токен через Siteverify; без
успешной серверной проверки заявка не создаётся.

## Безопасность загрузки изображений

Галерея, аватар и логотип принимают только JPG/JPEG, PNG и WEBP. Проверяется
реальный формат, соответствие расширению и полное декодирование изображения;
повреждённые и анимированные файлы отклоняются. Исходный файл не сохраняется:
фото пересоздаются в JPEG, логотип — в PNG с сохранением прозрачности, без
метаданных и дополнительных данных. Имена новых файлов генерируются случайно.

По умолчанию действуют ограничения:

- фото объекта — до 10 МБ; аватар и логотип — до 5 МБ;
- разрешение — до 25 миллионов пикселей;
- до 10 фото за одну загрузку и до 30 фото на объект.

Лимиты настраиваются через `PROPERTY_IMAGE_MAX_MB`, `PROFILE_IMAGE_MAX_MB`,
`IMAGE_UPLOAD_MAX_PIXELS`, `PROPERTY_IMAGES_PER_UPLOAD` и
`PROPERTY_IMAGES_MAX_COUNT`. Multipart-парсер дополнительно ограничен 20 файлами
на запрос. Если хотя бы одна фотография не проходит проверку, весь набор
отклоняется до сохранения. Эти правила действуют и для загрузки аватаров и
логотипов в Django Admin. Ранее загруженные файлы автоматически не исправляются.

Перед production-развёртыванием обязательно настройте раздачу `/media/` на
web-сервере или файловом хранилище: только разрешённые растровые форматы,
правильные MIME-типы, `X-Content-Type-Options: nosniff`, без выполнения скриптов,
листинга каталогов и доступа к файлам вне media-каталога. Предпочтительна
изоляция пользовательских файлов на отдельном домене, не просто поддомене
сайта. Ограничьте общий размер HTTP-запроса на reverse proxy: проверки Django
выполняются после приёма файлов и не заменяют защиту от заполнения диска или
DoS. Для стандартных лимитов галереи предел запроса должен учитывать до
100 МБ файлов плюс multipart-данные. Папку media нужно резервировать отдельно
от БД. Настройка сервера остаётся отдельным этапом развёртывания.

Основание: [рекомендации Django по пользовательским загрузкам](https://docs.djangoproject.com/en/6.0/topics/security/#user-uploaded-content).

## Юридические документы и персональные данные

Сервис содержит публичные страницы политики обработки персональных данных,
согласия и условий использования. При отправке заявки и регистрации пользователь
должен отметить отдельное согласие на обработку персональных данных; дата и
версия согласия сохраняются в базе. Для регистрации отдельно сохраняется
принятие условий сервиса.

Перед публикацией обязательно задайте реальные значения `LEGAL_OPERATOR_NAME`,
`LEGAL_OPERATOR_INN`, `LEGAL_OPERATOR_OGRN`, `LEGAL_OPERATOR_ADDRESS`,
`LEGAL_PRIVACY_EMAIL` и `LEGAL_DATA_STORAGE_LOCATION`. Шаблоны не заменяют
проверку юристом: особенно если данные передаются за пределы России, используются
внешние сервисы или меняется модель оказания услуг.

## Тестовый стенд на PythonAnywhere Free

Для демонстрации одному пользователю проект можно разместить на бесплатном
PythonAnywhere без отдельной платной базы: не задавайте `DATABASE_URL`, и
Django использует SQLite на стороне PythonAnywhere. ИИ на стенде отключён.

1. Создайте бесплатный аккаунт PythonAnywhere и откройте **Consoles → Bash**.
2. Создайте виртуальное окружение с Python 3.12 или новее (версия должна
   совпадать с версией будущего web app):

   ```bash
   mkvirtualenv --python=python3.13 realestate-ai
   git clone --branch staging https://github.com/Jovanovi4/realestate-ai.git
   cd realestate-ai
   pip install -r requirements.txt
   python manage.py migrate
   python manage.py collectstatic --noinput
   python manage.py createsuperuser
   ```

3. В **Web → Add a new web app** выберите **Manual configuration** и ту же
   версию Python. В поле **Virtualenv** укажите
   `/home/ВАШ_ЛОГИН/.virtualenvs/realestate-ai`.
4. Откройте WSGI-файл из вкладки Web и замените его содержимое на шаблон
   [deployment/pythonanywhere_wsgi.py.example](deployment/pythonanywhere_wsgi.py.example),
   подставив свой логин и новый секретный ключ. Секрет можно сгенерировать
   командой `python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"`.
5. В разделе **Static files** добавьте два соответствия:
   - `/static/` → `/home/ВАШ_ЛОГИН/realestate-ai/staticfiles`;
   - `/media/` → `/home/ВАШ_ЛОГИН/realestate-ai/media`.
6. Нажмите **Reload**. Сайт откроется по адресу
   `https://ВАШ_ЛОГИН.pythonanywhere.com`.

При обновлении стенда выполните в Bash-консоли:

```bash
workon realestate-ai
cd ~/realestate-ai
git pull origin staging
pip install -r requirements.txt
python manage.py migrate
python manage.py collectstatic --noinput
```

После этого нажмите **Reload** на вкладке Web. Не передавайте тестировщику
доступ администратора: создайте для него отдельный демо-аккаунт с тестовыми
данными.

## Тестовый стенд на Render

Проект подготовлен для отдельного стенда: PostgreSQL подключается через
`DATABASE_URL`, статика собирается WhiteNoise, а Gunicorn запускает Django.

1. В Render создайте PostgreSQL и Web Service из ветки `staging`.
2. В поле **Build Command** укажите `./build.sh`.
3. В поле **Start Command** укажите
   `gunicorn config.wsgi:application --bind 0.0.0.0:$PORT`.
4. Добавьте переменные окружения:
   - `DJANGO_SECRET_KEY` — новый случайный секрет;
   - `DJANGO_DEBUG=False`;
   - `DATABASE_URL` — внутренний URL базы PostgreSQL из Render;
   - `DJANGO_SERVE_MEDIA=True`;
   - `DJANGO_MEDIA_ROOT=/var/data/media`;
   - `AI_ENABLED=False` — отключает ИИ-помощника на демо-стенде.
5. Подключите постоянный диск Render в `/var/data`, чтобы загруженные
   фотографии не пропадали после нового развёртывания.
6. После первого запуска создайте отдельного администратора командой
   `python manage.py createsuperuser` в Render Shell. Не используйте
   стандартные или общие пароли.

Render автоматически задаёт `RENDER_EXTERNAL_HOSTNAME`; он используется как
разрешённый хост и CSRF-origin. При подключении собственного домена задайте
`DJANGO_ALLOWED_HOSTS` и `DJANGO_CSRF_TRUSTED_ORIGINS` явно.
